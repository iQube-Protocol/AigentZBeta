## Commit Message

```
Give Horizen registration confirmation independent server-side liveness

checkAgentRegistrationStatus() had exactly one caller: a browser poll capped
at 160s (RegisterAgentPanel.tsx). Once that poll gave up — page close,
disconnect, or a deploy mid-poll — a broadcast registration had nothing left
checking on it. Same defect class as the DVN finalizer's O-2 gap, same fix:
a scheduled reconciler (services/horizen/registrationReconciliation.ts) that
re-invokes the existing, unmodified check via a cron-token-gated route and
GitHub Actions workflow, mirroring activity-receipts-finalizer.yml exactly.

Never rebroadcasts — only calls checkAgentRegistrationStatus (step 3 of the
existing three-step flow). Agent-generic: resolves the subject agent from
the submitted receipt's own agentsInvoked via resolveRegistrableAgentByRuntimeId,
never a hardcoded slug. Idempotent: skips any submission that already has a
matching horizen_agent_registered receipt (read via the existing
findAgentRegistrationReceipts). One agent's failure never blocks another's
check in the same run.

Extracted the interactive status route's inline updateRegistryAssetBinding +
createRegistrationReceipt into services/horizen/registrationConfirmationDeps.ts
so both the interactive route and the new reconciler share one implementation
of what confirmation writes, instead of duplicating it.

Added findReceiptsByActionType to activityReceiptService.ts — the canonical
receipt reader's cross-persona counterpart to listActivityReceiptsForPersona,
needed because a scheduled reconciler has no persona to scope to.
```
