# CI × IRL × OCSGA — Pre-Experiment Boundary Map

**Status:** PROPOSED — Crucible / OCSGA dossier companion; pre-canon except where it cites already-ratified doctrine.  
**Date:** 2026-08-22  
**Programme:** Constitutional Internet × IRL × OCSGA  
**Parent dossier:** `ocsg-constitutional-agentic-network-experiment-proposal.md`  
**Purpose:** establish system boundaries before joint experimental design, preserving independent provenance and preventing terminology convergence from being mistaken for architectural compatibility.

## 1. Crucible candidates

### CAN-COMP-001 — Compatibility should be discovered before integration is designed
When independently developed systems appear complementary, their native boundaries, responsibilities, assumptions and interfaces should be mapped and tested before a joint architecture is designed. Integration should follow evidence of compatibility rather than manufacture compatibility through premature co-design.

Candidate compression:

> **Preserve independent boundaries first. Test the seams second. Co-design only where evidence establishes a genuine gap.**

Falsification / compression condition: if explicit boundary mapping adds no explanatory, experimental or integration value over direct co-design, or systematically obscures necessary coupled behavior, the candidate should be revised or rejected.

### CAN-COMP-002 — Discovered compatibility and created compatibility are evidentially distinct
Compatibility discovered between independently specified systems is evidentially different from compatibility created through mutual redesign, reinterpretation or extension. Both may be useful outcomes, but they answer different research questions and must not be reported as equivalent evidence of native architectural compatibility.

- **Discovered compatibility** — independently developed architectures retain their native purpose, primitives and responsibilities while exposing useful interfaces without material alteration.
- **Created compatibility** — useful composition requires one or more architectures to be redesigned, reinterpreted, extended or supplemented with a deliberately co-designed interface.

Candidate compression:

> **Discovering compatibility is evidence about the systems as they are. Creating compatibility is evidence about what the systems can become together.**

Methodological consequence: the classification must be fixed before cross-map comparison so that post-hoc redesign cannot be mistaken for evidence of pre-existing compatibility.

Falsification / compression condition: if the discovered/created distinction cannot be operationally determined, or does not change the interpretation of experimental evidence, CAN-COMP-002 should be revised, compressed into CAN-COMP-001 or rejected.

## 2. Research posture

CI, IRL and OCSGA were developed independently. Their potential composability is therefore treated as a hypothesis, not an assumed architecture.

The pre-experiment question is:

> **Are we testing architectural compatibility between independently existing systems, or attempting to co-design a new architecture?**

These are different research objectives and must not be conflated.

Initial posture: **architectural compatibility first**. Co-design is warranted only where the boundary exercise or later experiments reveal a genuine unresolved gap, conflict or missing interface.

## 3. Boundary-map method

For each system, establish independently:

1. **Native purpose** — what problem the system was designed to solve.
2. **Owned primitives** — concepts/states for which the system claims authoritative responsibility.
3. **Inputs** — what the system consumes but does not originate.
4. **Outputs** — what the system produces for other systems or actors.
5. **Assumptions** — conditions the system presumes to hold.
6. **Explicit non-responsibilities** — what the system does not claim to own or solve.

Only after those native definitions are recorded should interfaces be compared.

### Freeze/version discipline before exchange

Before either side sees the other's completed baseline:

- each native map should be completed independently;
- each map should be frozen/versioned with date and provenance;
- the frozen baseline should remain available after later revisions;
- post-exchange changes should be recorded as such rather than silently folded into the pre-comparison baseline.

This preserves a clean evidentiary distinction between native architecture and compatibility created after comparison.

## 4. Interface classification

Every proposed seam between CI, IRL and OCSGA should be classified without forced harmonization as one of:

- **COMPATIBLE** — independently defined responsibilities/interfaces compose without material redefinition.
- **AMBIGUOUS** — apparent compatibility exists but ownership, semantics or interface behavior is insufficiently specified.
- **CONFLICTING** — native definitions or operational requirements are incompatible.
- **REDUNDANT** — two systems appear to own substantially the same responsibility without demonstrated need for duplication.
- **UNRESOLVED** — evidence is insufficient to classify the seam.

A seam must not be labeled compatible merely because the systems use similar terminology.

Where an interface becomes compatible only after post-baseline redesign, extension or reinterpretation, it must be recorded as **created compatibility**, not retroactively classified as discovered native compatibility.

For each object ask:

2. Who has **authoritative custody/state**?

5. Who **consumes** the output?

## 7. Candidate operational chain to test, not assume

`Governance → Authority + Mandate + Control conditions`

`Proposed Action + Current State + Consequence Projection + A/M/C → Authorization`

`Authorization → Execution → Realized Consequence → Evidence → Updated State / Trust`

The boundary exercise must determine whether CI, IRL and OCSGA naturally expose interfaces that can support this chain. The chain must not be used to redefine any independent system merely to make the composition fit.

## 8. Admissible boundary-map outcomes

The exercise must allow at least these legitimate outcomes:

1. **Genuine discovered architectural compatibility** — native system boundaries remain intact and useful interfaces are discoverable without material redesign.
2. **Useful adjacency with limited interfaces** — the systems are related but do not constitute a broader composable architecture in all relevant respects.
3. **Overlap/conflict requiring co-design** — meaningful composition requires explicit redesign, new shared primitives or a negotiated interface; any resulting compatibility is created rather than discovered.

Outcome 2 or 3 is not experimental failure. Created compatibility may itself be valuable. Forcing Outcome 1, or retroactively presenting Outcome 3 as Outcome 1 after redesign, would invalidate the evidentiary distinction.

## 9. Independence discipline

Before comparison:

- MetaProof/IRL records CI and IRL boundaries from their native canon and implementation.
- Ian/OCSGA records OCSGA boundaries independently from OCSGA's native architecture.
- Neither side rewrites terminology merely to improve apparent fit.
- Each side freezes/versions its baseline before exchange.

During comparison:

- semantic similarity is not treated as architectural equivalence;
- duplicated primitives are surfaced rather than silently merged;
- incompatible assumptions are recorded as conflicts;
- missing interfaces are recorded as gaps rather than retroactively assigned to either system;
- any post-exchange change intended to improve composition is recorded as deliberate co-design and therefore created compatibility.

## 10. Gate to joint experiment design

A joint boundary-validation experiment should be designed only after:

- native purposes and responsibilities are recorded;
- owned primitives and explicit non-responsibilities are visible;
- both independent maps have been frozen/versioned before exchange;
- candidate interfaces are classified;
- unresolved ownership/semantic conflicts are identified;
- discovered compatibility is distinguished from any created compatibility;
- the parties can state whether the proposed experiment tests native compatibility or a deliberately co-designed interface.

The experiment should then perturb defined seams rather than shared terminology.

## 11. Relationship to Crucible methodology

This approach operationalizes the existing research maxim:

> **The goal is not to prove the architecture; it is to discover the minimum architecture that survives falsification.**

Boundary mapping is therefore not an integration exercise. It is a precondition for stronger falsification: each system must first be allowed to remain itself.

Candidate research progression:

`Independent native boundary capture → freeze/version → exchange → boundary comparison → seam classification → discovered-compatibility finding → experiment design → perturbation / ablation → evidence → minimum surviving architecture → deliberate co-design only where warranted → created-compatibility finding where applicable`
