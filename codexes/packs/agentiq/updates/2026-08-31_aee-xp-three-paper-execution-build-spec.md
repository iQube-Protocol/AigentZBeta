# 1. Constitutional state rule

Every executable experience begins by answering:

> **What state is this person actually in now, in this journey, under this authority, evidenced by which canonical sources?**

The Ian Boundary Research work established the reference pattern: one authoritative state assembly is shared across channels rather than allowing web, MCP, agents or other surfaces to reconstruct constitutional reality independently.

This programme generalizes the pattern, not Ian-specific code.

## 1.1 Read rule

> **Many channels may observe. One authoritative interpretation of relevant state must be composed from canonical state owners.**

## 1.2 Write rule

> **Many channels may invoke. One canonical constitutional transition primitive must govern a consequential state change.**

## 1.3 No global-state monolith

Do **not** create a new single mutable estate-wide state database.

Authoritative ownership remains distributed:

- Journey Spine owns journey progression.
- Constitutional systems own authority, delegation, authorization and canonical constitutional facts.
- Financial Services Runtime owns financial service state and capability outcomes.
- Research / IRL owns experiment state and research lifecycle.
- DevOn owns development-loop state.
- AR/CPS owns governed artifact-production state.
- ExQube owns experience-state evidence.
- DCIR owns consequential observation / validation events.
- DVN / receipts own evidence anchoring and verifiable transition evidence.
- AEE consumes bounded projections of these states; it does not become their source of truth.

Canonical rule:

> **One coherent state view; multiple authoritative state owners.**

# 5. New minimal primitive: Experience Handoff

A small provider-neutral handoff contract is required to move a person between journeys/surfaces without creating authority.

Suggested contract:

```ts
interface ExperienceHandoff {
  handoffId: string;
  participantRef: string;
  sourceJourneyId: string;
  sourceStageId?: string;
  targetJourneyId: string;
  targetSurfaceRef?: string;
  intent?: string;
  capabilityFocus?: string[];
  agentCandidateRef?: string;
  recommendedExperienceAltitude?: string;
  experienceEvidenceRefs?: string[];
  returnJourneyId?: string;
  returnStageId?: string;
  rationale?: string;
  createdAt: string;
  expiresAt?: string;
}
```

Rules:

- carries continuity, intent and bounded experience context;
- may carry an agent candidate, never a fabricated agent registration/delegation;
- may carry experience evidence references, never raw cross-context private data by default;
- MUST NOT assert constitutional authorization;
- target journey resolves authority/current state from its canonical owners;
- must support resume/return;
- must be surface/provider neutral;
- should be usable by web, native, MCP, agent and external-harness interactions.

Initial uses:

- KNYTS → Financial Services;
- CI → Financial Services;
- Financial Services → IRL;
- IRL → Financial Services;
- Financial Services → DevOn;
- DevOn → Financial Services;
- IRL → DevOn where research establishes an engineering implication.

# 7. XP-2 — State & Observation convergence

## Objective

Make the Ian-derived state pattern ubiquitous without creating a state monolith.

## Required pattern

Each journey/domain exposes an **authoritative state adapter** that composes the relevant canonical state owners into a bounded state projection suitable for Journey/AEE.

The adapter MUST NOT become a new source of truth.

Reference behavior:

```text
canonical owners
  ↓
authoritative state adapter
  ↓
Journey runtime state
  ↓
AdaptiveInteractionContext
  ↓
AEE
```

## Observation split

Do not build a duplicate general observation database.

- low-consequence experiential observations → ExQube / experience evidence;
- consequential outcome observations → DCIR;
- artifact production/publication state → AR/CPS;
- constitutional transitions → CTP / canonical state + receipts;
- AEE reads these outcomes and re-evaluates.

Canonical rule:

> **Recommendations observe produced state; they do not manufacture it.**

AEE MUST NOT mark a Journey stage or NBE complete because an agent claims completion. Completion comes from canonical evidence.

## R3 re-evaluation triggers

Implement a bounded trigger model for projection invalidation/recomposition, including as appropriate:

- Journey state changed;
- authority/delegation changed;
- Standing/qualification changed;
- user accepted/refused/deferred recommendation;
- experience evidence changed;
- AR artifact state changed;
- DCIR consequence observed;
- financial service state changed;
- experiment state changed;
- DevOn state changed;
- provider/surface/device conditions changed.

# 12. XP-7 — DevOn branch + CTP integration

## Objective

Make Development a first-class branch from Financial Services and Research, preserving evidence and state on return.

## Branch rule

Use DevOn when the system is known to require change.

Typical triggers:

- missing capability;
- implementation defect;
- constitutional gap;
- provider incompatibility;
- experience failure requiring software change;
- failed consequence;
- research finding with an engineering implication.

## Handoff

A DevOn handoff should preserve references to:

- originating journey/state;
- user/operator intent;
- capability ref;
- gap/anomaly evidence;
- applicable receipts;
- AR artifact refs;
- DCIR consequence refs;
- relevant experiment refs;
- relevant invariants/CTPs;
- return target.

Then reuse the existing DevOn state machine unchanged.

## Research ↔ DevOn routing

```text
Observed anomaly
  ↓
Known implementation defect? ── YES → DevOn
  │
  NO / uncertain
  ↓
IRL experiment
  ↓
validated finding
  ↓
engineering implication
  ↓
DevOn
```

A DevOn proposal may also branch into IRL before deployment where a behavioral/consequence claim is materially uncertain and needs experimental evidence.

## CTP awareness

Activate CTP-001's development rule as part of the implementation programme:

```text
Does this implementation change canonical / consequential state?
  │
  NO → normal implementation path
  │
  YES
  ↓
identify active CTP
  ├── exists → reuse/invoke canonical primitive
  └── absent → constitutional gap; do not invent direct mutation
```

CTP remains a separate implementation workstream because the charter currently records doctrine/design but does not itself implement the constitutional runtime, CTP registry, schema or CI enforcement.

The first CTP migration should follow the charter's own priority/OCSGA-first sequencing rather than attempting an estate-wide big-bang rewrite.

# 16. Capstone acceptance journey

The programme is not complete until the following can be demonstrated end-to-end with real authoritative state and evidence.

## Main path

1. Person enters **KNYTS Bridge** or **CI Bridge**.
2. Journey state is resolved from authoritative evidence.
3. aigentMe/AEE determines a Financial Sovereignty NBE.
4. AEE presents an appropriate DISCOVER/LEARN/EXPLORE experience.
5. Person selects a Financial Services path and an agent candidate is prepared.
6. `ExperienceHandoff` moves the person to the Financial Services Bridge.
7. FS Bridge resolves canonical state; no state is trusted merely because the source Bridge supplied it.
8. Agent is registered using the existing registration capability.
9. Existing Claim/Orient/Passport/Activate/Delegate states proceed as required.
10. Person reaches professional Operate state.
11. MoneyPenny Advisor is used for an informational action.
12. Architect produces a proposal/artifact through governed artifact machinery where applicable.
13. A consequential Runtime action invokes native constitutional authorization and existing governance path.
14. Receipt and realized consequence are observed.
15. AEE recomputes the Next Best Experience from resulting state.

## Research branch

16. A financial-services question is identified as experimentally uncertain.
17. AEE/aigentMe offers Research as NBE.
18. `ExperienceHandoff` branches into the appropriate IRL onboarding/workspace/journey.
19. Experiment/protocol/evidence use canonical IRL state.
20. Experiment can be inspected/reviewed from an FS-projected Research surface and/or entered from IRL into the actual FS experimental surface.
21. Findings/Crystal/review complete as applicable.
22. Person resumes the originating FS journey with evidence refs preserved.

## DevOn branch

23. An implementation gap is identified from FS directly or from the research result.
24. `ExperienceHandoff` creates a DevOn branch with source evidence.
25. Existing DevOn stages run from intent to deployment authorization.
26. If canonical/consequential state is affected, the relevant CTP is identified or a constitutional gap is raised.
27. Implementation is validated and deployed through existing authorization discipline.
28. Person resumes FS context.
29. DCIR observes resulting consequence.
30. AEE recomputes NBE from the new state.

Passing this one journey proves Papers I, II and III are executable as one system.
