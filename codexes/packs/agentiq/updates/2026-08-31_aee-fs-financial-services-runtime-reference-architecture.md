## 0. Executive proposition

The Financial Services Runtime is the first vertically integrated reference environment for the Adaptive Experience Engine.

It is not merely a financial-services application and not merely MoneyPenny's interface. It is the complete constitutional experience stack through which a person can discover, understand, design, authorize, execute, observe and learn from financial-services activity while preserving personhood, authority, provenance, evidence and consequence across changing interfaces.

The central proposition is:

> **Financial capability is stable; the experience through which a person reaches and uses it may adapt continuously to their person, persona, journey, authority, standing, intent, risk, context and observed consequence.**

The Financial Services vertical therefore gives AEE a bounded domain in which to prove deep integration from experience research through constitutional execution and back into software development:

# 2. Existing estate foundation

This architecture is an evolution of a substantial existing implementation, not a speculative rewrite.

The current estate already establishes several load-bearing separations that AEE-FS must preserve.

## 2.1 Financial Services Bridge

The Financial Services Bridge already exposes the same canonical Horizen × MoneyPenny journey through public bridge routes without forking journey state, receipt logic or capability implementation.

The Bridge therefore already embodies a core AEE law:

> **A new interface should project an existing journey and capability, not create a second constitutional implementation.**

## 2.2 Journey Spine

The Horizen × MoneyPenny journey already models meaningful progression through states such as Register, Claim, Orient, Passport, Activate, Delegate, Operate and the consequence fork.

Journey completion is evidence-based rather than page-based.

AEE must consume this progression; it must never replace it.

## 2.3 MoneyPenny

MoneyPenny is already ratified as the primary Constitutional Financial Services Agent and operates in three canonical provider modes:

- **Advisor** — grounded, cited, read-only financial guidance;
- **Architect** — proposes and designs financial structures and artifacts;
- **Runtime** — acts within bounded, receipted, delegated authority.

MoneyPenny specializes the financial-services lens. She does not create a second constitutional reasoning or settlement engine.

## 2.4 Financial-service consequence taxonomy

The Financial Services Runtime already separates provider-specific mode from generic consequence class:

```text
MoneyPenny ADVISOR   → INFORMATIONAL
MoneyPenny ARCHITECT → PROPOSAL
MoneyPenny RUNTIME   → CONSEQUENTIAL
```

This distinction is essential for AEE.

`ADVISOR / ARCHITECT / RUNTIME` describes **how a provider serves the participant**.

`INFORMATIONAL / PROPOSAL / CONSEQUENTIAL` describes **what class of consequence the service carries**.

A future provider may use completely different mode names while still mapping into the same constitutional consequence taxonomy.

## 2.5 Multiple Runtime governance paths

The existing service catalog also proves that a single experiential mode may contain multiple constitutional execution mechanisms.

MoneyPenny currently exposes two distinct Runtime services:

- **MoneyPenny Runtime (Constitutional)** — governed by the existing Constitutional Service Pipeline;
- **MoneyPenny Runtime (Confidential)** — governed by Constitutional Commerce / VELA and confidential consequence projection.

Both are consequential.

They must not be collapsed merely because both are called Runtime.

This gives AEE-FS a critical architectural principle:

> **Experience mode does not determine governance path. Governance path is resolved independently from the actual capability and consequence.**

# 4. The person-centred financial context

The AEE should never adapt Financial Services from a generic customer profile alone.

It operates over a bounded financial interaction context anchored in personhood and scoped progressively through persona, relationship, journey and interaction.

Conceptually:

```text
Person
  ↓
Persona
  ↓
Financial relationship / programme
  ↓
Financial journey
  ↓
Current financial intent
  ↓
Conversation / workflow / exchange
  ↓
Current authority + Standing + wallet state
  ↓
Current surface / host / device
```

This allows a person's durable financial rights, credentials, capabilities and Standing to remain coherent without allowing confidential financial information to leak indiscriminately across personas or interactions.

For Financial Services this distinction is particularly important because the same person may participate as, for example:

- an individual consumer;
- a founder;
- an authorized officer of an organization;
- an investor;
- a researcher;
- a creator;
- or an agent principal.

The person remains constitutionally continuous.

The active persona determines which identity, relationship, mandate, disclosure and financial context may be projected into the present interaction.

# 6. Financial Experience Matrices

Experience Matrices map the model's dimensions into valid experience patterns.

AEE-FS should maintain several matrices rather than a single monolithic rule table.

## Matrix A — participant state × experience pathway

Example:

| Participant state | Likely experience emphasis | Typical MoneyPenny mode | Constitutional boundary |
|---|---|---|---|
| Exploring an unfamiliar financial concept | explanation, glossary, examples, Companion guidance | Advisor | read-only |
| Comparing possible structures | matrices, scenarios, cited reasoning | Advisor / Architect | no execution |
| Designing a product or arrangement | structured design canvas, assumptions, artifacts | Architect | proposal only |
| Preparing to act | consequence preview, readiness, authority state | Runtime orientation | authorization boundary visible |
| Ready for consequential action | minimal necessary confirmation + native constitutional ceremony | Runtime | platform-owned execution |
| Waiting on settlement/counterparty | status, receipts, next valid condition | Advisor / Runtime status | no fabricated progress |
| Reviewing completed activity | evidence, receipts, consequence comparison | Advisor / research | read-only |

The matrix does not automatically select a provider. It describes the experience pattern.

## Matrix B — MoneyPenny mode × consequence class × governance path

| Provider mode | Consequence | Governance path | AEE treatment |
|---|---|---|---|
| Advisor | INFORMATIONAL | NONE | highly adaptable; read-only |
| Architect | PROPOSAL | NONE | compositional/generative artifact experience; never imply authorization |
| Runtime | CONSEQUENTIAL | CONSTITUTIONAL_SERVICE_PIPELINE | adaptive pre/post execution; constitutional execution remains platform-owned |
| Runtime | CONSEQUENTIAL | CONSTITUTIONAL_COMMERCE | adaptive pre/post execution; confidential projection, attestation and execution controls remain governed by VELA path |

This matrix prevents AEE from treating all Runtime experiences as one interchangeable mechanism.

## Matrix C — rendering mode × consequence

| Rendering mode | Informational | Proposal | Consequential |
|---|---|---|---|
| R0 Fixed | valid | valid | preferred for invariant ceremonies where clarity is critical |
| R1 Templated | valid | valid | valid within bounded fields |
| R2 Compositional / Generative | strong fit | strong fit | pre/post-action only unless generated composition is restricted to approved constitutional primitives |
| R3 Adaptive | strong fit | strong fit | valid around the act; may not dynamically rewrite the canonical act itself |

## Matrix D — surface residency

Every material Financial Services surface should be classified:

- `NATIVE_ONLY`;
- `NATIVE_PREFERRED`;
- `HYBRID_ALLOWED`;
- `EXTERNAL_RENDER_ALLOWED`;
- `EXTERNAL_HOST_ALLOWED`.

Residency is independent from rendering mode.

A native surface can be adaptive.

An externally hosted surface can be fixed.

A generative composition may legitimately hand off into an R0 native ceremony for signing, key use or authorization.

## Matrix E — feedback signal × adaptation authority

| Signal | May influence projection? | May change constitutional truth? |
|---|---:|---:|
| declared experience preference | yes | no |
| observed navigation pattern | yes, proportionately | no |
| inferred preference | yes, with provenance/confidence | no |
| Journey state | yes | no — Journey owns it |
| Standing | yes | no — Standing owner controls it |
| wallet state | yes | no |
| successful/failed service outcome | yes | no |
| consequence divergence | yes, strongly | no — may trigger review/remediation |
| receipt / evidence state | yes | no |
| provider recommendation | candidate only | no |

# 7. Adaptive rendering modes in Financial Services

AEE-FS adopts the AEE-001B rendering spectrum.

## R0 — Fixed

The same approved structure is rendered deterministically.

Financial examples:

- principal authorization ceremony;
- signature flow;
- wallet key operation;
- legally/constitutionally required disclosure;
- canonical receipt detail where representation must not drift.

Fixed does not mean primitive or poor UX. It means the structure is intentionally invariant.

## R1 — Templated

A stable component accepts bounded context and content.

Examples:

- financial status card;
- service eligibility panel;
- standardized risk summary;
- balance / transaction card;
- standing state;
- journey stage explanation.

## R2 — Compositional / Generative

The runtime dynamically assembles approved primitives.

Examples:

- a MoneyPenny Advisor answer containing a comparison matrix, evidence capsule and recommended next-step pill;
- an Architect experience combining assumptions, scenario cards, artifact preview and approval pathway;
- a service chooser composed according to current intent and eligibility;
- a contextual dashboard assembled from journey, wallet, receipt and research modules.

AEE-FS follows the governing principle:

> **Generate the composition more readily than the constitutional primitive.**

The components may be dynamically assembled; their underlying authority and semantics remain governed.

## R3 — Adaptive

An R2 or other valid experience becomes adaptive when the system continuously observes changing context and can recompose accordingly.

Examples:

- a novice receives explanatory Advisor-first orientation; after repeated successful use, the same service becomes denser and more direct;
- a participant planning a transfer sees simulation and consequence explanation until authority, Standing and wallet conditions are satisfied, then receives a concise authorization handoff;
- after a failed authorization or unavailable settlement rail, the interface stops foregrounding execution and recomposes around remediation;
- a pending transaction changes the experience from action-oriented to evidence/status-oriented without requiring a new application flow;
- a participant moves from desktop Bridge to mobile Companion while preserving Journey and authority context but changing modality and density.

Adaptive therefore means:

```text
Sense → Understand → Determine → Compose → Project → Interact → Observe → Adapt ↺
```

Generative UI without this feedback loop is R2, not R3.

# 9. Experience selection versus service execution

AEE may determine that the appropriate next experience is, for example:

> “The participant needs a comparison of treasury structures before selecting one.”

It may therefore project an Architect experience.

That does not mean AEE executes Architect itself.

The separation is:

```text
AEE
  decides: what experience / capability is appropriate
        ↓
Financial Service Orchestration
  resolves: which service/provider can fulfil it
        ↓
MoneyPenny / provider
  performs: Advisor / Architect / Runtime work
        ↓
Governance path
  determines: what constitutional mechanism governs consequence
```

This prevents AEE from becoming a second financial-services orchestrator.

# 10. Advisor experience

Advisor is the lowest-consequence and therefore broadest adaptive surface.

The Advisor experience may safely vary substantially in:

- explanation depth;
- information density;
- terminology;
- examples;
- visualization choice;
- comparison format;
- order of evidence;
- Companion involvement;
- recommended next actions;
- degree of active guidance.

However, the adaptive layer must preserve:

- grounding and citation provenance;
- distinction between evidence and interpretation;
- no implication that advice is authorization;
- no conversion of recommendation into financial execution;
- persona/context disclosure boundaries.

Advisor is therefore a strong early Differ / adaptive-provider target.

---

# 11. Architect experience

Architect converts intent and evidence into proposed structures or artifacts.

The adaptive opportunity is larger than a form-builder.

An Architect experience may dynamically compose:

- objectives;
- assumptions;
- constraints;
- alternative structures;
- scenario comparisons;
- pricing or fee models;
- delegation envelopes;
- settlement terms;
- evidence;
- draft agreements;
- artifact previews;
- ratification steps.

The critical constitutional rule is:

> **A generated financial structure is a proposal until constitutionally ratified.**

AEE may optimize how the structure is explored and understood.

It must not make proposal state look like authorized state.

# 12. Runtime experience

Runtime is where adaptive experience approaches the constitutional execution boundary.

The correct architecture is not to disable adaptation entirely, but to place it around an invariant governed act.

```text
Adaptive orientation
        ↓
Consequence / readiness projection
        ↓
Canonical authorization / execution ceremony
        ↓
Observed consequence
        ↓
Adaptive status / explanation / remediation
```

The central design rule is:

> **The experience around a consequential act may adapt; the meaning and authorization of the act may not.**

AEE may change how readiness is explained, which evidence is foregrounded, what remediation path is offered, and how completed consequence is displayed.

It may not manufacture authorization or substitute a generated control for the canonical execution mechanism.

# 13. Two Runtime paths, one experiential family

The current estate contains two real MoneyPenny Runtime capabilities.

## 13.1 Constitutional Runtime

The existing MoneyPenny Constitutional Runtime uses the Constitutional Service Pipeline and the existing constitutional agreement / authorization mechanism.

From an experience perspective, AEE may present it as a Runtime option where the intended consequence fits that capability.

From a governance perspective, the AEE must preserve its existing pipeline.

## 13.2 Confidential Runtime

The Confidential Runtime uses Constitutional Commerce / VELA, requires consequence projection, confidentiality and attestation constraints, and is structurally fail-closed when required assurance is unavailable.

AEE must therefore treat confidential readiness as part of experience state.

For example, if the required attestation environment is unavailable, the correct adaptive response is not to hide the failure or route around it. The experience should recompose toward explanation, simulation, alternative capability, waiting or remediation.

This illustrates a key AEE principle:

> **A refusal or unavailable constitutional condition is itself an experience state.**

# 15. Financial Services Bridge as AEE front door

The Bridge should evolve from a fixed public entrance into the principal Financial Services Journey projection surface.

It should not become a parallel application.

The Bridge's job is to:

- establish the current participant and threshold state;
- project the relevant Financial Services Journey;
- orient the person to available capabilities;
- foreground the appropriate service experience;
- preserve Companion continuity;
- hand off to native constitutional surfaces where required;
- return the participant to the same Journey after the act.

AEE can progressively replace “one default screen for everyone” with context-sensitive foregrounding while preserving the canonical Journey definition underneath.

# 16. Companion and MoneyPenny roles

Companion and MoneyPenny should remain distinct even when their visible interaction becomes seamless.

**Companion** provides persistent relational and journey orientation across the wider metaMe estate.

**MoneyPenny** is the specialist Financial Services agent.

A Financial Services experience may therefore transition naturally between:

- Companion explaining where the participant is;
- MoneyPenny advising on the financial matter;
- AEE composing the appropriate surface;
- a native constitutional action;
- Companion resuming the journey afterward.

The participant should not need to understand these architectural boundaries for the experience to remain constitutionally correct.

# 17. Provider architecture — Differ and other adaptive renderers

Differ is the reference external adaptive provider, not the definition of AEE.

A Financial Services provider may provide some combination of:

- hosting;
- observation;
- adaptive recommendations;
- rendering;
- component composition;
- navigation presentation;
- presentation-state persistence.

Every provider receives only bounded projections appropriate to its verified capability and disclosure class.

Provider recommendations are candidate experience projections.

They must pass platform validation before application.

Canonical rule:

> **The provider may recommend or render the financial experience. metaMe determines what is true, available, authorized and evidenced.**

# 18. CopilotKit in the Financial Services stack

CopilotKit is best treated as an orchestration/composition mechanism rather than as the Adaptive Experience Engine itself.

It may help:

- orchestrate agent/tool calls;
- select or populate approved components;
- drive conversational UI;
- assemble generative compositions;
- connect contextual assistance to backend actions.

A CopilotKit-generated or orchestrated experience becomes AEE-governed only when it is receiving bounded AEE context/projection and participates in the closed-loop adaptive model.

Therefore:

```text
AEE              = adaptive decision / control loop
CopilotKit       = possible orchestration/composition mechanism
Differ           = possible external host/observer/renderer
Native renderer  = deterministic/platform rendering mechanism
```

These are complementary roles, not competing definitions.

# 22. IRL — the Financial Services experience laboratory

The Invariant Research Lab should treat the Financial Services Runtime as the first controlled AEE field environment.

This allows the estate to test questions such as:

- Does an adaptive Advisor experience improve comprehension without increasing error?
- Which information-density patterns reduce time-to-value?
- When should the system move from explanation to direct action?
- Which signals reliably indicate increased financial capability?
- Does adaptive service selection reduce abandoned journeys?
- Does a generated composition improve outcome over a fixed template?
- Which surfaces can be externally hosted without weakening authority or privacy?
- When does an experience inference become misleading?
- Does preserving continuity across native and externally hosted surfaces improve task completion?
- How should refusal and waiting be represented so they improve trust rather than appear as system failure?
- What is the relationship between Standing, demonstrated capability and appropriate autonomy?
- Does consequence-aware feedback improve future decision quality?

AEE decisions should therefore be experimentally observable rather than treated as unexamined personalization.

# 23. Invariant discovery

Financial Services provides a natural environment for discovering three related classes of invariant.

## Experience invariants

Example hypothesis:

> Consequential financial authorization should remain visually and semantically distinct from proposal generation regardless of adaptive provider.

## Constitutional invariants

Example hypothesis:

> The principal/delegate distinction must remain invariant across every financial-service surface and provider.

## Engineering invariants

Example hypothesis:

> Any externally generated Financial Services projection must validate against the same canonical Journey and authorization state as the native projection.

These remain hypotheses until validated through the appropriate research / ratification process.

The AEE paper does not mint them as canonical merely by naming them.

# 27. Fallback and resilience

A Financial Services adaptive provider must never become the only route to a constitutionally required act.

For every critical surface:

- native fallback must exist;
- provider outage must not change Journey truth;
- provider failure must not manufacture completion;
- provider recommendation failure must not alter authorization;
- critical financial state must remain reconstructible from platform truth;
- a participant must be able to complete required constitutional actions through a platform-owned route.

AEE therefore improves experience without becoming a single point of constitutional failure.

# 28. Reference implementation programme

The next implementation work should be divided into bounded increments.

## FS-A — Financial Experience Model v0.1

Define the typed Financial Services experience context and model dimensions without creating a parallel AEE runtime.

## FS-B — Financial Experience Matrices v0.1

Encode the principal participant-state, MoneyPenny-mode, consequence, rendering-mode and residency matrices.

Begin as explicit data/rules so they can be inspected and tested.

## FS-C — Financial Experience Projection

Extend/reuse the provider-neutral `ExperienceProjection` to carry Financial Services-specific refs rather than forking the core type unnecessarily.

## FS-D — Bridge integration

Feed the current Financial Services Bridge and Journey Spine into the AEE context builder.

Shadow mode first: generate an adaptive projection without changing live navigation.

## FS-E — MoneyPenny service selection

Allow AEE to recommend/foreground Advisor, Architect or Runtime service families while leaving actual service resolution and execution in the existing Financial Services orchestrator.

## FS-F — Rendering spectrum

Prove at least one surface in each appropriate rendering mode:

- R0 fixed;
- R1 templated;
- R2 compositional;
- R3 adaptive.

## FS-G — Differ shadow / hosted experiment

Use the bounded Financial Services projection package and provider validation path. Auto-apply remains off until explicitly authorized and validated.

## FS-H — Hybrid constitutional handoff

Demonstrate a coherent journey from adaptive/external surface → native constitutional action → adaptive/external continuation.

## FS-I — IRL experiment

Define a falsifiable experiment comparing at least native fixed/templated and adaptive composition for one low-risk Financial Services journey slice.

## FS-J — Invariant / development feedback

Feed validated findings into IRL / invariant discovery and DevOn without treating user-behavior correlation as canon automatically.

# 29. Success criteria

The Financial Services Runtime becomes the AEE reference implementation when:

1. Financial Services has an explicit Experience Model and inspectable Experience Matrices.
2. AEE can consume canonical Journey, authority, Standing, wallet, service and experience projections without duplicating their ownership.
3. AEE can distinguish provider mode, consequence class and governance path.
4. The same canonical financial capability can be reached through multiple surfaces without semantic drift.
5. At least one useful R3 adaptive Financial Services surface is live or experimentally proven.
6. A generated/compositional experience can hand off to an invariant native constitutional act and resume coherently afterward.
7. External providers receive only bounded provider-safe data projections.
8. Provider failure falls back to a deterministic native experience.
9. Financial-service outcomes and consequence evidence return into the adaptive loop.
10. IRL can compare projections and outcomes with explicit hypotheses and evidence.
11. No adaptive layer can create authority, authorization, Journey completion or receipts.
12. Experience improvements can be converted into engineering work through IDE 2.0 / DevOn without bypassing constitutional review.

# 31. Canonical operating principles for AEE-FS

1. **The person is the financial continuity anchor.** Accounts and screens are not.
2. **Persona controls contextual expression and disclosure.** Continuity does not imply context collapse.
3. **Journey owns progression.** AEE does not fabricate financial progress.
4. **Experience Model defines possibility; Experience Matrix maps context; AEE chooses/composes projection.**
5. **Provider mode, consequence class and governance path are separate axes.**
6. **Advisor informs; Architect proposes; Runtime may act only through governed authority.**
7. **Generate compositions more readily than constitutional primitives.**
8. **Adaptive experience surrounds consequential acts; it does not redefine them.**
9. **Refusal, waiting and remediation are legitimate experience states.**
10. **Wallet and constitutional ceremonies retain native sovereignty where required.**
11. **Providers receive projections, not financial sovereignty.**
12. **Observed consequence closes the adaptive loop.**
13. **IRL turns adaptation into experiment; invariants require evidence.**
14. **DevOn turns validated learning into governed software change.**
15. **Financial Services is the reference vertical; MetaNite / Knights Bridge is a later application of it.**

# 32. Architectural compression

The reference architecture can be expressed in one sequence:

> **A person enters the Financial Services Journey through an appropriate persona. Journey Spine establishes where they are. Financial Experience Models and Matrices describe what is appropriate. AEE composes the next valid experience. A renderer or host manifests it. MoneyPenny or another provider performs the required financial service. Constitutional mechanisms govern consequential acts. Wallet and settlement rails realize authorized action. DVN and receipts record what happened. IRL observes the consequence. Validated findings improve the next experience and the next generation of the runtime.**

Or more simply:

> **Learn → Understand → Design → Authorize → Act → Evidence → Learn again — adapted to the person, bounded by the constitution.**
