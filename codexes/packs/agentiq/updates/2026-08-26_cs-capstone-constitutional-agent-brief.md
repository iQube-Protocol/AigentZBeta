# CS Capstone Brief — Constitutional Agent or Agentic Service

**Artifact:** CS-CAPSTONE-BRIEF-001  
**Cohort:** Lehigh Undergraduate Computer Science Capstone  
**Status:** OPERATING BRIEF / IMPLEMENTATION-GROUNDED  
**Submission environment:** Invariant Research Lab OS Workspace  
**Primary destinations:** DevOn or Financial Services Runtime

## 1. Required outcome

Design, implement, evidence and demonstrate one bounded agent or agentic service that is admissible to the Constitutional Computing platform and can be consumed by:

1. **DevOn**, as a reusable development capability; or
2. the **Financial Services Runtime**, as an admitted financial-services agent/capability.

An assurance or stress-testing project is acceptable where its output is itself a reusable capability, reproducible test instrument or consequential evidence package.

“Admissible” does not mean that every student artifact becomes canonical automatically. The contribution record should join the capstone lineage; the implementation, claims and capability must still pass review, admission and any separate freeze/canonization/publication authority.

## 2. Existing platform: reuse before extension

The brief configures existing architecture rather than creating a parallel capstone system.

| Need | Existing surface to reuse | Student obligation |
|---|---|---|
| Project home | Registered CS capstone cohort and student-project workspaces | Work only in the assigned project scope. |
| Lifecycle | Shared `capstone` lifecycle template | Progress through all nine stages and preserve stage evidence. |
| Development method | DevOn, Registry resolution and IRG | Prove what was reused, extended and newly created. |
| Collaboration | IRL OS Working Materials and QubeTalk | Keep mutable drafts separate from review artifacts. |
| Evidence | Workspace Activity/receipts and review package | Make consequential claims traceable and reproducible. |
| Participation | Student Researcher role | Submit artifacts and receive attributable contribution receipts without acquiring canonization authority. |
| Credit admission | Shared V-10 Standing gate | Claim only permitted, evidenced contribution bases; never quantity metrics. |

## 3. Track selection

### Track A — DevOn capability

Build an agent/helper that DevOn can invoke during constitutional development. Suitable areas include Registry discovery, IRG analysis, invariant discovery, test/canary generation, evidence packaging, provenance, repair-risk analysis, consequence projection, or admission checks.

The service must expose a stable callable contract, declare its inputs/outputs and refusal conditions, and demonstrate how it reduces an identified IRG without duplicating an existing capability.

### Track B — Financial Services agent or service

Build an agent/capability usable within the Financial Services Runtime. Suitable areas include bounded research, data verification, risk analysis, compliance evidence, simulation, portfolio/service analysis, reconciliation, or non-custodial workflow assistance.

Any money-moving, signing, wallet, personal-data or regulated action must fail closed outside explicitly granted authority. A convincing mock or simulation is preferable to a falsely “live” execution claim.

### Track C — Constitutional assurance

Build a reusable stress-test, adversarial evaluation, conformance harness or runtime canary for DevOn or the Financial Services Runtime. It must detect a meaningful class of failure, preserve evidence and be callable/re-runnable—not merely describe risks in a report.

## 4. Mandatory Intent-to-Registry Gap analysis

Before implementation, submit an IRG record containing:

1. **Intent:** the user or system outcome in one falsifiable statement.
2. **Registry search:** relevant capabilities found, including near matches.
3. **Reuse decision:** what will be consumed unchanged.
4. **Extension decision:** what existing capability will be extended and why.
5. **Creation delta:** the smallest capability that genuinely does not exist.
6. **Invariant set:** what must remain true across the end-to-end path.
7. **Consequence model:** intended outcome, foreseeable adverse consequences, refusal conditions and recovery path.
8. **Time to value / risk of repair:** how reuse reduces delivery time without hiding downstream repair risk.
9. **Registration plan:** how the proven result becomes discoverable for subsequent builders.

A project that rebuilds an existing Registry capability without an evidenced reason is not complete.

## 5. Required delivery package

Each project must submit:

- project and capability identifier;
- problem statement and IRG record;
- architecture and trust-boundary description;
- declared invariants and executable conformance tests;
- callable interface or agent contract;
- authority scope, delegation assumptions and refusal behavior;
- source code with reproducible build/run instructions;
- automated unit/integration tests and at least one end-to-end canary;
- evidence package: inputs, outputs, receipts, logs and known limitations;
- security/privacy analysis appropriate to the data tier;
- Registry/admission manifest with version and provenance;
- demonstration scenario and concise operator documentation;
- final contribution statement describing individual authorship and team dependencies.

The package must not include production credentials, private wallet material or personal identifiers.

## 6. Admission criteria

The capability is **DevOn-grade** or **Financial-Services-grade** only when all applicable criteria pass:

| Criterion | Required evidence |
|---|---|
| Registry fit | Search record, reuse/extend/create ruling and non-duplication rationale |
| Callable contract | Versioned interface, schemas, error/refusal behavior and sample invocation |
| Bounded authority | Explicit scope; no self-delegation; privileged actions fail closed |
| Invariant grounding | Falsifiable invariants mapped to tests/canaries and runtime observations |
| Consequence completeness | Intended and adverse consequences, recovery and risk-of-repair assessment |
| Reliability | Repeatable tests, deterministic fixtures where appropriate, observable failures |
| Provenance | Source/version/dependency lineage and attributable artifact receipts |
| Privacy/security | Data classification, minimum disclosure and no secret material in artifacts |
| Runtime fit | Demonstrated invocation in the selected destination or a faithful integration harness |
| Operability | Setup, monitoring, refusal, rollback/disable and known-limit instructions |

Claims unsupported by evidence are not admission evidence. A correct refusal or honest negative result may be a stronger contribution than an unsafe apparent success.

## 7. IRL lifecycle and submission route

The project must use the existing lifecycle verbatim:

1. **Brief** — accept the brief and select a track.
2. **Research Plan** — define intent, users, methods, risks and success criteria.
3. **Source/Data Review** — complete Registry search, source evaluation and data-rights review.
4. **Build or Analysis** — implement the IRG delta and preserve working evidence.
5. **Review** — submit an immutable review package; reviewers do not edit source assets.
6. **Revision** — answer findings with traceable changes or evidenced objections.
7. **Submission** — submit the complete admission package.
8. **Demonstration** — run the declared scenario and failure/refusal case.
9. **Archive/Commons** — preserve the accepted contribution record and authorized artifacts in lineage.

## 9. Constitutional attribution and Standing

### What is guaranteed by the operating model

- The student is the attributable contributor; the school and workspace do not own the student's constitutional contribution.
- Student Researchers may receive attributable contribution receipts for work in assigned projects.
- A contribution can remain in project lineage after the semester and can be cited by the contributor.
- Grading cannot directly create, remove or substitute for Standing.
- Admission is based on verified contribution quality—such as correctness, veracity, proof quality, reproducibility, reliability, authority compliance and honest negative results—not activity volume.

### Canonical lineage versus canonical content

The accepted contribution record may be canonized into the platform's lineage while the content it contains retains its own status. This prevents “student submitted it” from becoming “the platform ratified every claim in it.” Freeze, canonization and publication require separate authorized acts; workspace membership grants none of them.

### Current implementation dependency

The shared V-10 gate can evaluate a research contribution and return an admission decision. Automatic mapping from that admitted signal into Personal, Delegated, Stewardship or Capability Standing is explicitly deferred as **Slice C**. Therefore:

- receipts and admission decisions should be issued and preserved now;
- no submission-, commit-, hour- or artifact-count proxy may be substituted;
- no one should claim that automatic Standing accrual is live until Slice C is implemented and tested;
- closure of Slice C is a platform dependency for final automatic constitutional-credit issuance, not a student deliverable unless explicitly assigned as a Track C project.

## 10. Definition of done

A capstone is complete for platform purposes when:

- all nine lifecycle stages have evidential records;
- the IRG demonstrates reuse before extension and creation;
- the capability has a Registry/admission manifest;
- the agent/service is callable in, or through a faithful harness for, DevOn or the Financial Services Runtime;
- invariant, authority, consequence, security and failure-path evidence passes review;
- the demonstration includes both intended success and refusal/failure behavior;
- contribution authorship is receipted and preserved in the IRL lineage;
- publication/canonization status is stated accurately; and
- any admitted-but-unaccrued Standing signal is labeled as such.
