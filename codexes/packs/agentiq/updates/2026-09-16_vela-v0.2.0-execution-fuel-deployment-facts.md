# Vela v0.2.0 execution, fuel, and deployment-identity facts — version-scoped record (2026-09-16)

**Status: version-scoped facts about the DEPLOYED v0.2.0 substrate, not future capability
claims.** This doc records what Horizen's own feedback (2026-09-16, relayed after the public
devnet run documented in `2026-09-14_vela-public-devnet-v0.2.0-milestone.md`) established, and
what this codebase changed in response. Read this before touching Vela result-reading, fuel/fee
code, or anything claiming to know "which WASM an applicationId is."

## 1. Reconstructed application identity — `applicationId` alone proves nothing

`applicationId` is an integer the chain assigns on deploy. It carries no intrinsic binding to any
WASM artifact. The binding is a **chain of evidence**:

```
deploy transaction input (carries the WASM sha256, unencrypted)
  -> DeployRequestSubmitted (binds that deploy request to the assigned applicationId)
  -> DeployRequestCompleted (proves the deployment actually SUCCEEDED, for that applicationId/requestId)
```

**Implementation:** `services/vela/velaApplicationDeploymentReceipt.ts` — the canonical
`VelaApplicationDeploymentReceipt` type, `assembleVelaApplicationDeploymentReceipt` (from raw,
already-fetched chain evidence — the deploy step's own job) and
`verifyVelaApplicationDeploymentReceipt` (re-verifies a persisted receipt, purely locally, no
network call). Fails closed on: missing transaction input, mismatched request/application IDs,
mismatched WASM hashes, a failed deployment status, or malformed/incomplete evidence.

`scripts/vela/public-devnet-smoke.ts`'s deploy step now **independently decodes the deploy
transaction's own input** (never merely trusts the Authority Service's upload-response echo) and
writes a verified receipt to `scripts/vela/.public-devnet-smoke-deployment-receipt.json`.

`scripts/seedUseCaseZeroDemo.ts` now **requires** `--deployment-receipt=<path>` for any
consequential (non-`--preflight`) FROZEN run — a naked `--app=<number>` is no longer sufficient. The
receipt's `applicationId` is what flows through Factor selection, disclosure authorization, envelope
composition, and the Vela submission itself; `--app` is superseded, never silently trusted instead,
when both are given.

## 2. Authoritative completion-before-output rule

`ProcessorEndpoint.RequestCompleted.status` (0 = completed, 1 = failed) is the **authoritative**
completion signal — checked BEFORE any output (`UserEvent`/`AppEvent`/state change) is trusted.
`errorCode`/`errorMessage` carry the specific reason when `status !== 0`, never the primary check.

**Implementation:** `VelaRequestResult` (`services/vela/velaTypes.ts`) now carries `status` and
`applicationFees` (previously unread from the real `RequestCompleted` event entirely) alongside the
pre-existing `errorCode`/`errorMsg`, plus `prevStateRootHex` (the `StateRootUpdate.oldStateRoot`
paired with the existing `stateRootHex`/`newStateRoot`). `getVelaMultiPartyProjectionOutcome`
(`services/vela/velaMultiPartyProjection.ts`) now gates on `status !== 0 || errorCode !== 0` (either
signal alone is sufficient to fail closed — this only ever widens failure detection, never narrows
it) before it will call `parseConfidentialVerdict` on any decoded output. `pollMultiPartyDispositionToTerminal`
(`services/vela/velaUnderwritingProjection.ts`) threads `applicationFees`/`stateRootHex`/
`prevStateRootHex`/`stateUpdateTxHash` into the persisted causal receipt (field 9, additive to the
existing eight-element binding) — the ACTUAL fee charged and the exact state transition, never
inferred from successful submission alone.

## 3. Execution Failure Non-Equivalence (pre-existing, from 2026-09-14; unchanged in substance)

Already ratified as `CI-2026-09-14-EXECUTION-FAILURE-NON-EQUIVALENCE-001`. Restated here because
this pass's `status`-based hardening is an extension of it, not a replacement:
`getVelaMultiPartyProjectionOutcome`'s `EXECUTION_FAILED` branch is structurally distinct from
`RESOLVED` — there is no `disposition` field reachable on the failure branch without a TypeScript
narrowing check. A failure to execute (an Executor/fee problem) must never be interpreted as a
constitutional determination the guest actually computed.

**`INSUFFICIENT_FUEL` is error code 12 on the DEPLOYED v0.2.0 ABI** — pinned as
`VELA_V0_2_0_ERROR_CODES.INSUFFICIENT_FUEL` in `services/vela/velaFuelAccounting.ts`. The unreleased
v0.3.0 renumbers this; never use that numbering against the current deployment.

## 4. v0.2.0 fuel is guest-self-reported, never host-metered

Vela v0.2.0 does not meter guest execution. The guest returns its own `Fuel` value on every
successful call; the Executor sums it and charges `fuel * EXECUTOR_FUEL_PRICE_PER_UNIT`, subject to
`minFeePerRequest`. A client can predict what the guest will self-report; it cannot verify the guest
was actually metered — that is a substrate property, not something closeable client-side.

**The MoneyPenny guest's own current values** (`services/vela/wasm/projector/app/app.go`, cited by
exact line, mirrored — never re-derived by formula since the guest reports a flat constant per
entry point regardless of party count or payload shape):

| Entry point | Fuel units | Source line |
|---|---|---|
| `Deploy` | 5 | app.go:86 |
| `LoadModule` | 5 | app.go:94 |
| `DepositFunds` | 5 | app.go:103 |
| `ProcessRequest` (single- or multi-party) | 25 | app.go:168 |

**Implementation:** `services/vela/velaFuelAccounting.ts` — `GUEST_SELF_REPORTED_FUEL_UNITS` (the
table above) and `computeVelaFeeReservation` (deterministic: `expectedFuelUnits * price`, floored to
`minFeePerRequest`, then explicit headroom applied — never a bare hardcoded wei literal at a call
site). `scripts/vela/public-devnet-smoke.ts`'s `buildPartyRig` now reads `minFeePerRequest()` live
on-chain and computes its `maxFeeValueWei` reservation through this formula instead of the prior
`1_000_000n` hardcode.

**Price/minimum provenance — devnet observations, not protocol constants.** On the public devnet
observed 2026-09-14: 1 wei/fuel unit, 10 wei minimum (a request needing 25 wei failed when only 10
was supplied, then completed once submitted with 25 — the formula above now reaches that same 25
figure by calculation, proven in `tests/vela-fuel-accounting.test.ts`). `DEVNET_OBSERVED_FUEL_PRICE_WEI_PER_UNIT`/
`DEVNET_OBSERVED_MIN_FEE_PER_REQUEST_WEI` exist ONLY as an explicitly-labelled fallback
(`FuelPriceProvenance.source: 'devnet-observed-fallback'`) for a caller with no live on-chain read —
`minFeePerRequest()` itself has an on-chain getter and is read live wherever practical; the
per-fuel-unit price has no on-chain getter anywhere in this codebase today.

## 5. Per-application-only native isolation (unchanged, restated)

Vela provides isolation only per `applicationId`. Participant/organization isolation **inside** a
shared MoneyPenny application (party namespace refs, COMPUTE_WITH/DISCLOSE_TO scoping,
non-transitivity) is entirely the WASM's own responsibility — already implemented in
`evaluateMultiParty`/`buildMultiPartyEvents` (app.go) and the TypeScript-side scope-binding gates
(`services/vela/velaMultiPartyProjection.ts`). Not touched this pass; recorded here as a fact this
pass's other changes depend on.

## 6. One recipient per `UserEvent`

`buildMultiPartyEvents` (app.go:717) emits exactly one `PlainEvent` per authorized party ref, each
addressed (`UserID`) to that party's own recipient address — the Executor encrypts to ONE
registered P-521 key per event. Already correctly implemented; this pass added explicit proof tests
(`tests/vela-multi-party-projection.test.ts`, the two new gate-4 cases: asymmetric one-directional
disclosure showing distinct per-party dispositions, and a never-invited outsider resolving the
conservative `UNRESOLVED`) rather than rewriting working logic.

## 7. Externally frozen freshness (unchanged, restated)

There is no trusted current time inside the guest. The block timestamp supplied with a request can
be delayed. Freshness policy (how stale is too stale) must be decided and enforced OUTSIDE Vela —
e.g. `composeUnderwritingAdmissionEvidence`'s own `maxAssessmentAgeMs` freshness check
(`services/vela/velaUnderwritingAdmissionEvidence.ts`) already follows this discipline for Aegis
admission evidence. Not modified this pass; recorded as a constraint any future Vela-adjacent
freshness logic must respect.

## 8. Current absence of native retirement, migration, and recovery-policy observability

Vela v0.2.0 has **no native mechanism** for: retiring/disabling a deployed application, exporting or
migrating private state between deployments, or observing/attesting a recovery/KMS policy for the
TEE signer's key material. None of these exist in this codebase either — correctly, since inventing
a client-side workaround for a substrate gap the protocol itself does not support would be exactly
the kind of fabricated capability CLAUDE.md's No-Guessing rule forbids. `VelaApplicationDeploymentReceipt.ephemeral`
records that a public-devnet `applicationId` will not survive that devnet's periodic resets — this
is disclosure of the gap, not a workaround for it.

## Future primitives — named, NOT implemented this pass

Recorded so a future pass has a starting vocabulary; none of the below exists in this codebase
today, and nothing in this pass should be read as claiming otherwise:

- **Application disable/retirement action** — no protocol mechanism exists to retire a deployed
  `applicationId`; a future client-side "soft retirement" record (marking an applicationId as
  no-longer-trusted in this codebase's own evidence, independent of anything on-chain) is a
  plausible shape, not designed here.
- **Private-state export/import or migration action** — no protocol mechanism exists to move a
  deployed application's private state to a new deployment. Any future migration would need its
  own explicit, evidenced protocol this codebase does not yet have.
- **Signer/P-521 rotation and namespace migration** — `services/vela/agentP521Derivation.ts`
  derives one P-521 key deterministically per EVM signer today; rotating that signer (or the P-521
  key independent of it) and migrating existing namespace refs to the new derivation is unscoped.
- **Custom AuthorityService and WASM constitutional disclosure gate** — this codebase uses only the
  admin-whitelisted default AuthorityService (Horizen finding 17 names an application-owned custom
  AuthorityService as an alternative). Any additional constitutional authorization beyond what
  `app.go`'s own COMPUTE_WITH/DISCLOSE_TO scoping enforces would need to live inside the WASM, per
  Horizen's own guidance — not designed here.
- **Recovery-policy attestation** — Horizen's finding 20: recovery/KMS policy is not currently
  observable or attestable. No client-side substitute is proposed; this is recorded as an open gap,
  not something this codebase can currently verify or work around.

## Known, disclosed limitation carried forward from this pass (not silently "fixed")

`transport.fetchResult`'s decrypt loop (`VelaClientAdapter`, real transport) treats EVERY decrypt
failure identically to "this UserEvent was not addressed to me" (per `VELA-PRIVACY-BOUNDARY-001`).
This is correct for the common case (a party genuinely not granted `DISCLOSE_TO`), but it also means
a genuinely-authorized party whose decrypt fails for an UNRELATED reason (a registered-key mismatch,
corrupted on-chain data) is currently indistinguishable from "not authorized" — both resolve to the
conservative `UNRESOLVED` via `parseConfidentialVerdict(null)`. This pass did not change that
behavior: the privacy-boundary code is explicitly documented as tested/proven, and closing this
ambiguity would need either a protocol-level signal Vela v0.2.0 does not expose, or a larger,
riskier change to privacy-sensitive decrypt logic than this pass's scope justified. Flagged here for
explicit operator awareness rather than left undocumented.
