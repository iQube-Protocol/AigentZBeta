# VL-INV-001 — IRG, Circular Development and Consequence Engineering

**Status:** PROPOSED-FOR-CANONIZATION  
**Roadmap:** CFS-051 / Roadmap A — Proposed Invariants  
**Recorded:** 26 August 2026  
**Source:** VL-CANON-2026-06-08  
**Promotion boundary:** none of these propositions is canonical under an `inv.*` identifier until the existing human canonisation ceremony completes.

## Reconciliation

These proposals recover June 2026 doctrine and reconcile it with:

- Experience Sovereignty and Experience Vibing;
- the iQube Registry operating plane;
- DevOn and the Development Command Center;
- Consequence Engineering;
- CFS-040 Knowledge Resolution Engine;
- the Golden Rule in `AGENTS.md`: reuse first, extend second, create only where no suitable capability exists.

They deepen the later reuse-before-create direction. They must not be seeded as duplicate canonical invariants without a corpus-equivalence review.

## Candidate 1 — Intent resolves against governed capability

**Slug:** `intent-resolves-against-governed-capability`  
**Class:** structural / engineering  
**Status:** proposed-for-canonization

> A consequential build begins by resolving its authorised intent against governed, deployable and reusable capability already present in the iQube Registry; otherwise the system cannot distinguish a real capability gap from avoidable redevelopment.

**Failure condition:** implementation begins without an evidenced Registry resolution or an explicit reason the Registry is unavailable/inapplicable.

**Likely enforcement:** DevOn intent intake requires a Registry Resolution Report or a recorded exceptional disposition.

## Candidate 2 — IRG bounds original development

**Slug:** `irg-bounds-original-development`  
**Class:** engineering / economic  
**Status:** proposed-for-canonization

> Original development is bounded by the Intent-to-Registry Gap: the smallest unresolved distance between an authorised sovereign intent and the governed capabilities presently resolvable through the Registry.

**Failure condition:** the implementation scope materially exceeds the evidenced gap without a new authorised intent or consequence decision.

**Likely enforcement:** gap manifest links each newly created component to an unresolved requirement.

## Candidate 3 — Reuse before extend before create

**Slug:** `reuse-extend-create-order`  
**Class:** engineering  
**Status:** proposed-for-canonization

> Proven capability is reused before it is extended, and extended before a parallel capability is created, because preserving accumulated evidence reduces time-to-value, duplicated labour and risk-of-repair.

**Failure condition:** a parallel implementation is introduced while a sufficient governed capability exists and no explicit incompatibility or risk disposition is recorded.

**Likely enforcement:** architecture plans and PRDs carry a required reuse / extend / create table; canaries reject unacknowledged parallel primitives in protected domains.

## Candidate 4 — Validated resolution returns to the Registry

**Slug:** `validated-irg-resolution-returns-to-registry`  
**Class:** structural / regenerative  
**Status:** proposed-for-canonization

> A capability created or extended to close an IRG completes its development cycle only when its governed record, boundaries, provenance and validation evidence return to the Registry for future resolution and reuse.

**Failure condition:** production capability closes a local intent but remains undiscoverable or lacks a governed Registry record.

**Likely enforcement:** deployment completion requires a Registry reference or a documented non-reusable classification.

## Candidate 5 — Consequence precedes code

**Slug:** `consequence-precedes-code`  
**Class:** constitutional engineering  
**Status:** proposed-for-canonization

> Consequential code is justified by an intended and authorised consequence model before implementation, because capability without a bounded outcome cannot be evaluated for benefit, legitimacy or risk-of-repair.

**Failure condition:** consequential implementation proceeds without an explicit intended outcome, affected subjects, authority basis and repair-risk analysis.

**Likely enforcement:** DevOn consequence-model stage gates implementation authorisation.

## Candidate 6 — End-to-end consequence validates the delta

**Slug:** `end-to-end-consequence-validates-delta`  
**Class:** epistemic / engineering  
**Status:** proposed-for-canonization

> Closing an IRG is established by end-to-end observed consequence and evidence, not by local code completion alone; therefore implementation, integration, deployment and runtime effect remain one validation object.

**Failure condition:** a capability is marked complete solely because code or isolated tests pass while deployment or consequential outcome remains unobserved.

**Likely enforcement:** consequence-validation receipt links intent, Registry substrate, delta, deployment and observed outcome.

## Candidate 7 — Productive effort accumulates

**Slug:** `productive-effort-accumulates`  
**Class:** economic / sovereignty  
**Status:** proposed-for-canonization

> Validated human and synthetic effort should accumulate as reusable governed capability rather than be repeatedly consumed recreating solved work, so that agency is directed toward unresolved consequential gaps.

**Failure condition:** recurrent equivalent builds occur without reuse analysis or Registry improvement.

**Likely enforcement:** repeated-IRG telemetry; reuse ratio; duplicate-capability review; time-to-value and risk-of-repair comparison.

## Proposed derived measures

These measures are candidates for research and DevOn telemetry, not yet constitutional laws:

- **IRG size:** count or weighted complexity of unresolved capability requirements.
- **Reuse ratio:** governed reused capability divided by total capability required for the outcome.
- **Delta ratio:** newly created/extended capability divided by total capability required.
- **IRG closure time:** authorised intent to admitted reusable Registry capability.
- **Consequence realisation time:** authorised intent to observed useful outcome.
- **Risk-of-repair:** expected consequential cost of correcting the implementation after deployment.
- **Regenerative return:** future intents resolved by the newly registered capability.
