# QubeTalk Communications Membrane — Domain Specification v0.2

**Status:** RATIFICATION CANDIDATE — extends existing QubeTalk Peer Exchange; does not fork it  
**Date:** 2026-08-25  
**Area:** QubeTalk · metaMe Communications · Polity Passport · delegated agents · publishing · social engagement · receipts

## 0. Relationship to the existing QubeTalk implementation

This specification **extends** the existing QubeTalk constitutional and implementation spine. It does not replace or duplicate it.

Existing authority and shipped substrate:

- `codexes/packs/agentiq/updates/2026-07-20_prd-qubetalk-peer-exchange.md`
- `codexes/packs/agentiq/updates/2026-07-21_qubetalk-peer-exchange-phase1-build.md`
- `passport_peer_channels` / `passport_peer_messages`
- `services/qubetalk/peerChannel.ts`
- `/api/qubetalk/peer-channels/...`
- tenant `qubetalk_channels` runtime substrate
- `passport_qubetalk_channels` holder↔delegate substrate
- QubeTalk receipts / DVN-anchorable consequential actions
- locker sharing and rights-envelope semantics

The July Peer Exchange PRD fixed the constitutional semantics that remain binding here:

1. personhood-bound continuity;
2. bounded delegation;
3. no agent-initiated re-delegation;
4. explicit content rights;
5. receipts for consequence;
6. privacy / minimum disclosure;
7. reuse-first, no parallel QubeTalk system.

This v0.2 expands QubeTalk from personhood-bound peer exchange into a **platform-agnostic communications membrane** spanning private messaging, group conversation, publishing and engagement while preserving those invariants.

# 1. Core proposition

QubeTalk is **not chat** and is not merely a unified inbox.

> **QubeTalk is the sovereign communications membrane that maintains conversational continuity between people, groups and their delegates across platforms and over time.**

A platform thread is only a **transport span** inside a longer relationship or conversation.

Example:

```text
Monday     Dele → John      Email
Wednesday  Dele → John      WhatsApp
Friday     John → Dele      Telegram
June       John comments    LinkedIn
July       Dele → John      Signal
```

QubeTalk must be able to understand all of these as interaction between the same two principals while preserving the original transport, audience and social context of every event.

Primary invariant:

> **Relationship continuity > channel continuity.**

Corollary:

> **Continuity never erases provenance, audience boundaries, persona boundaries or delegated-authority boundaries.**

# 2. Communications planes

QubeTalk has three correlated but distinct planes on one substrate.

## 2.1 Messaging plane

Private and semi-private bidirectional communication:

- native QubeTalk / metaMe;
- email;
- WhatsApp;
- Telegram;
- Signal where API access permits;
- Messenger;
- LinkedIn messages;
- X direct messages where API access permits;
- Discord DMs/channels;
- future transports.

Canonical abstraction: **ConversationQube** within a **RelationshipQube** or **GroupQube**.

## 2.2 Publishing plane

One-to-many communication:

- Qriptopian;
- LinkedIn posts/articles;
- X posts/threads;
- Facebook;
- Instagram;
- Discord announcements;
- Medium;
- Substack;
- future publishing surfaces.

Canonical abstraction: **PublicationQube** with one or more platform projections.

## 2.3 Engagement plane

Responses generated by publication:

- comments;
- replies;
- mentions;
- quote-posts;
- reactions;
- questions;
- DMs arising from a publication.

Canonical abstraction: **EngagementQube**.

Engagement can resolve into an existing participant/relationship and become a ConversationQube.

```text
Publication → Engagement → Participant resolution → Relationship → Conversation
```

# 4. Core Qube types

The suffix `Qube` denotes the logical domain object; exact persistence names are implementation details and must reuse/extend the existing QubeTalk substrate where possible.

## 4.1 ParticipantQube

Represents a communication participant: person, delegated agent, organization, group endpoint, or unresolved correspondent.

A human participant should bind to personhood/identity infrastructure when available, but QubeTalk must also support ordinary external contacts without Passport membership.

Conceptual schema:

```json
{
  "participantId": "qtp_...",
  "kind": "person",
  "displayName": "John Doe",
  "principalRef": "optional-polity-public-reference",
  "identityConfidence": "user_confirmed",
  "endpoints": [
    {"platform":"email","address":"john@example.com","state":"verified"},
    {"platform":"whatsapp","address":"+44...","state":"user_confirmed"},
    {"platform":"telegram","address":"@john","state":"high_confidence"}
  ]
}
```

Allowed identity-confidence states:

```text
verified
user_confirmed
high_confidence
tentative
unresolved
```

### Participant invariant

Endpoints MUST NOT be merged solely because display names match.

When confidence is insufficient, QubeTalk preserves separate participants until the user or an authoritative resolver confirms linkage.

---

## 4.2 RelationshipQube

Represents the longitudinal communications relationship between principals across platforms and time.

It is **not** a transcript. It is the stable relationship container into which source-preserving communication events can be indexed.

Conceptual schema:

```json
{
  "relationshipId": "qtr_...",
  "principalRef": "owner-principal-ref",
  "counterpartyParticipantId": "qtp_...",
  "state": "active",
  "startedAt": "...",
  "lastInteractionAt": "...",
  "preferredEndpoints": [],
  "activeConversationIds": [],
  "sharedGroupIds": [],
  "agentPolicyRef": "...",
  "derivedState": {
    "summary": "...",
    "openLoops": [],
    "commitments": [],
    "activeTopics": []
  }
}
```

### Relationship derived memory

QubeTalk may maintain a rolling relationship summary and open-loop state, but:

- it MUST be derived from immutable source events;
- material assertions MUST be traceable to source message/event IDs;
- derived memory MUST NOT overwrite the historical record;
- persona/privacy/delegation boundaries constrain what an agent may retrieve from the relationship.

### Relationship states

```text
active
quiet
restricted
archived
```

A relationship does not become "closed" merely because one conversation ends.

---

## 4.3 GroupQube

Represents a persistent collective/social context that may itself span platforms.

Examples:

- Horizon Pilot Team;
- family group;
- Centralized AI Agent Alliance;
- Meta Knights investors;
- project or client teams.

Conceptual schema:

```json
{
  "groupId": "qtg_...",
  "name": "Horizon Pilot Team",
  "purpose": "Pilot coordination",
  "state": "active",
  "memberships": [],
  "transportEndpoints": [
    {"platform":"whatsapp","externalGroupId":"..."},
    {"platform":"discord","externalGroupId":"..."},
    {"platform":"metame","externalGroupId":"..."}
  ],
  "conversationIds": [],
  "agentPolicyRef": "..."
}
```

### Temporal membership

Group membership MUST be time-aware.

```json
{
  "participantId":"qtp_...",
  "joinedAt":"...",
  "leftAt":null,
  "role":"member"
}
```

A participant joining today MUST NOT be assumed to have been part of an earlier audience.

### Audience snapshot invariant

Every group/public message must preserve an **audience snapshot or reconstructable audience reference at event time**. Current membership cannot be substituted for historical audience.

## 4.4 ConversationQube

Represents a coherent topic, episode or conversational context. It may be direct, group, public-thread-based or federated across transports.

Conceptual schema:

```json
{
  "conversationId":"qtc_...",
  "relationshipId":"qtr_optional",
  "groupId":"qtg_optional",
  "topology":"dyadic",
  "topic":"Horizon Vela integration",
  "state":"open",
  "participantIds":[],
  "transportThreadRefs":[],
  "startedAt":"...",
  "lastActivityAt":"...",
  "agentPolicyRef":"...",
  "derivedState": {
    "summary":"...",
    "openQuestions":[],
    "commitments":[],
    "nextActions":[]
  }
}
```

### Conversation topology

Initial topology vocabulary:

```text
dyadic         1 ↔ 1
group          N ↔ N
broadcast      1 → N
fan_in         N → 1
public_thread  publication-centered multi-party thread
federated      one logical conversation across multiple transport contexts
```

Topology is distinct from transport.

### Conversation states

```text
open
dormant
resolved
archived
```

A resolved conversation may reopen or spawn a new linked conversation; the RelationshipQube continues regardless.

## 4.5 MessageQube

Represents one immutable communication event.

```json
{
  "messageId":"qtm_...",
  "conversationId":"qtc_...",
  "externalMessageId":"...",
  "transport":"whatsapp",
  "direction":"inbound",
  "senderParticipantId":"qtp_...",
  "recipientParticipantIds":[],
  "groupId":"qtg_optional",
  "audienceRef":"qta_...",
  "principalRef":"...",
  "actingAgentId":null,
  "delegationReceiptId":null,
  "replyToMessageId":null,
  "messageType":"message",
  "body":"...",
  "attachments":[],
  "occurredAt":"...",
  "ingestedAt":"...",
  "classification":{},
  "delivery":{},
  "receiptId":null
}
```

### Message immutability

The canonical event record MUST preserve the exact source event/provenance. Edits/deletes/reactions become subsequent events or state transitions; they do not silently rewrite history.

### Message social-context invariant

A group message may contribute to a RelationshipQube view, but it MUST remain a group message. Shared-context communication never becomes private communication merely because two participants know each other directly.


### Publication invariant

Platform projections are adaptations of one canonical publication act, not independent source documents unless explicitly promoted to separate works.

# 5. Relationship continuity and multi-context indexing

A single MessageQube may legitimately appear in multiple **views** without being duplicated.

Example: John posts in the Horizon WhatsApp group.

```text
MessageQube
   ├── authored_by → John ParticipantQube
   ├── belongs_to → Horizon GroupQube
   ├── belongs_to → Vela Integration ConversationQube
   ├── contributes_to → Dele↔John RelationshipQube
   └── transported_by → WhatsApp endpoint
```

The source record remains singular.

### Positive invariant

> QubeTalk may aggregate context across platforms while preserving the exact social context and audience of each event.

### Negative invariant

> QubeTalk MUST NOT flatten all interactions with a person into one undifferentiated transcript.

# 6. Context and disclosure boundary

Cross-platform continuity must not become context leakage.

The system must distinguish:

- private direct context;
- group context;
- organizational/project context;
- public context;
- persona/role context;
- agent-authorized context.

Before any outbound response, the effective context is:

```text
available authorized context
∩ current persona/role
∩ agent delegation
∩ destination audience
∩ disclosure policy
∩ consequence policy
=
disclosable context
```

### Core invariant

> **Context can inform; audience constrains disclosure.**

An agent may know a private fact that helps interpret a group discussion but may not reveal it to the group unless disclosure is separately authorized.

---

# 7. Endpoint and participant resolution

Every inbound event passes through participant resolution.

Resolution order should prefer:

1. explicit verified endpoint binding;
2. user-confirmed endpoint binding;
3. authoritative Passport/public-ref binding where available;
4. high-confidence match offered for confirmation;
5. unresolved participant preserved separately.

No fuzzy merge may silently combine participants.

### Endpoint state

```text
verified
user_confirmed
high_confidence
tentative
revoked
unavailable
```

Endpoint linkage is communications metadata, not a replacement identity system.

---

# 8. Group resolution

External group threads may map to a logical GroupQube.

Examples:

```text
WhatsApp "Horizon Pilot"
Discord #horizon-pilot
metaMe Horizon group
        ↓
GroupQube: Horizon Pilot Team
```

Cross-platform group federation requires explicit admin/user confirmation or an authoritative mapping. Similar names alone are insufficient.

A GroupQube may contain multiple ConversationQubes for distinct topics.

---

# 9. Conversation resolution and threading

Conversation assignment should be conservative.

An incoming event may:

1. attach to the explicit transport thread's current ConversationQube;
2. attach to an existing logical conversation with strong contextual evidence;
3. create a new ConversationQube;
4. remain temporarily unclassified.

Conversation merging/splitting must be reversible and preserve source references.

QubeTalk should prefer **episodic coherence** over forcing every message with one person into the same conversation.

---

# 10. Agent-management modes

Every relationship/group/conversation may specify an agent policy.

Canonical modes:

```text
manual
agent_drafts
agent_routine
agent_bounded
no_agent
```

Meaning:

- `manual` — user reads/sends; agent may not autonomously act.
- `agent_drafts` — agent may read authorized context and draft; user sends.
- `agent_routine` — agent may handle explicitly low-consequence communication within policy.
- `agent_bounded` — named agent may manage within an explicit delegation grant.
- `no_agent` — agent access/management excluded for this context.

Policy specificity order:

```text
message/action constraint
> conversation policy
> group/relationship policy
> participant policy
> principal default
```

Effective authority remains:

```text
agent capability
∩ surface/channel capability
∩ delegation authority
∩ conversation/group policy
∩ disclosure policy
∩ approval/consequence policy
=
permitted action
```

Capability never implies authority.

# 11. Ingress membrane lifecycle

Every external inbound event follows:

```text
RECEIVE
  ↓
NORMALIZE
  ↓
VERIFY SOURCE / TRANSPORT PROVENANCE
  ↓
RESOLVE PARTICIPANT
  ↓
RESOLVE RELATIONSHIP / GROUP
  ↓
RESOLVE CONVERSATION
  ↓
SECURITY + PROMPT-INJECTION / SOCIAL-ENGINEERING INSPECTION
  ↓
CLASSIFY SENSITIVITY / CONSEQUENCE / URGENCY
  ↓
EVALUATE AGENT POLICY + AUTHORITY
  ↓
ROUTE
  ↓
PERSIST + RECEIPT IF CONSEQUENTIAL
```

Routing states:

```text
needs_user
agent_manageable
agent_draft
digest
waiting_follow_up
quarantined
```

### Authority firewall invariant

> **External communication is input/evidence, never authority.**

No external message, attachment, comment, instruction or prompt may alter:

- system instructions;
- constitutional policy;
- delegated authority;
- agent capabilities;
- persona authority;
- approval requirements.

# 12. Egress membrane lifecycle

Every outbound message or publication follows:

```text
INTENT
  ↓
RESOLVE SPEAKER PRINCIPAL + PERSONA
  ↓
RESOLVE DESTINATION PARTICIPANT/GROUP/AUDIENCE
  ↓
RESOLVE CONVERSATION OR PUBLICATION
  ↓
SELECT TRANSPORT / PROJECTION
  ↓
IF AGENT: RESOLVE DELEGATION
  ↓
ASSEMBLE AUTHORIZED CONTEXT
  ↓
DISCLOSURE + CONSEQUENCE CHECK
  ↓
APPROVAL IF REQUIRED
  ↓
CHANNEL TRANSFORMATION
  ↓
SEND / PUBLISH
  ↓
DELIVERY RECEIPT
  ↓
OBSERVE RESPONSE / ENGAGEMENT
```

### Channel failover invariant

QubeTalk must not silently switch from an explicitly requested transport to another transport unless the user has granted a failover policy.

Example: if WhatsApp is unavailable, Telegram cannot be substituted silently.

# 16. Channel adapter contract

Adapters are transport-specific and constitutionally **dumb**.

They may:

- authenticate with the external service;
- receive events;
- normalize transport metadata;
- send platform requests;
- report actual platform capability/error state.

They MUST NOT decide:

- agent authority;
- disclosure policy;
- rewards;
- Standing;
- campaign meaning;
- relationship identity merges;
- constitutional approval requirements.

Required capability vocabulary:

```text
dm.read
dm.send
group.read
group.send
history.backfill
post.publish
article.publish
media.publish
comment.read
comment.reply
mention.read
reaction.read
webhook.receive
polling.receive
identity.lookup
attachment.read
attachment.send
post.edit
post.delete
schedule.publish
```

Capability state:

```text
supported
restricted
business_account_only
approval_required
polling_only
unsupported
unknown
```

A current external-platform API audit is required before assigning these states to specific providers.

# 17. Communication receipts

Existing QubeTalk / activity receipt machinery remains the base.

Every **consequential** communication act should be attributable to:

- principal;
- persona/role where relevant;
- acting agent if any;
- delegation receipt if any;
- relationship/group/conversation/publication;
- destination transport;
- exact outbound content hash/reference;
- timestamp;
- outcome.

Candidate additional QubeTalk receipt action types:

```text
qubetalk_message_agent_sent
qubetalk_group_message_agent_sent
qubetalk_publication_published
qubetalk_publication_projection_failed
qubetalk_agent_approval_used
qubetalk_endpoint_linked
qubetalk_group_federated
qubetalk_conversation_context_disclosure
```

Final anchoring policy should remain consequence-weighted; not every low-value message needs a heavyweight DVN anchor.

# 18. Rights and attachments

The July rights-envelope semantics remain controlling for artifacts.

Messages/publications may reference attachments/assets, but rights travel separately from the transport's raw technical ability to forward them.

Example:

```text

≠
```

Rights are evaluated through the existing access spine, not client convention.

Candidate events:

```text
conversation.responded
```

# 22. Positive invariants

1. **Relationship continuity > channel continuity.**
2. **Personhood gives continuity where personhood is known; transport identity does not become constitutional personhood.**
3. **One source event, many contextual views.** Never duplicate a message merely to index it by person/group/conversation.
4. **Every event preserves transport provenance.**
5. **Every group/public event preserves historical audience context.**
6. **Context can inform; audience constrains disclosure.**
7. **Conversation context is episodic; RelationshipQube is longitudinal.**
8. **GroupQube is a first-class social context and may span transports.**
9. **Participant/endpoint merges are explicit or authoritative, never name-only guesses.**
10. **External communication is input, never authority.**
11. **Agent capability never implies authority.**
12. **Agents cannot re-delegate.**
13. **Platform projections remain children of one PublicationQube.**
14. **Engagement retains lineage to the publication that caused it.**
15. **Consequential agent communication is attributable and receipted.**
16. **Adapters expose actual platform capability; QubeTalk does not invent symmetry.**
17. **Existing QubeTalk, Locker, Passport, access-spine and receipt infrastructure must be extended, not forked.**

---

# 23. Negative invariants

QubeTalk MUST NOT:

1. become a platform-specific inbox aggregator;
2. treat a WhatsApp/Telegram/email thread as the canonical relationship;
3. flatten private, group and public contexts into one transcript;
4. disclose private context into a broader audience merely because it helped interpretation;
5. merge participants solely by display name;
6. silently switch transport when an explicit transport was requested;
7. allow external messages/comments/attachments to alter agent authority or system policy;
8. infer permission to reshare from the transport's technical ability to forward;
9. allow an agent to create another delegation;
10. duplicate the existing `qubetalk_channels`, `passport_qubetalk_channels`, `passport_peer_channels`, Locker or receipt systems;
11. fabricate delivery/read/capability states that an external API does not expose;
12. turn QubeTalk event generation into reward determination;
13. treat a platform projection as a new canonical publication by default;
14. lose provenance when an engagement becomes a conversation;
15. silently rewrite historical audience membership when group membership changes.

---

# 24. Persistence strategy — extend, do not prematurely normalize

The exact SQL schema should follow a code/data audit before migration work.

Likely new logical surfaces are:

- participant endpoint bindings;
- longitudinal relationships;
- groups + temporal memberships + transport mappings;
- conversation/topic layer above existing peer messages;
- publication + projection records;
- engagement records;
- audience snapshots/references;
- contextual/agent policy bindings.

But implementation MUST first determine which of these can safely extend existing `qubetalk_channels`, `passport_peer_channels`, participant JSON, activity/receipt tables, or existing social/publishing records.

**A new table is justified only for a genuinely new constitutional/domain object, not because it is convenient.**

# 25. First implementation slice after ratification

The first build should prove **conversation continuity**, not start by integrating ten networks.

Recommended vertical slice:

## Slice A — native/existing QubeTalk + one external messaging transport

1. Introduce ParticipantQube endpoint binding.
2. Introduce RelationshipQube above existing peer channels.
3. Introduce ConversationQube classification/threading above existing messages.
4. Introduce GroupQube + temporal membership model.
5. Normalize existing peer messages into the new view without rewriting their source records.
6. Integrate **one** external messaging adapter with reliable API access (selected after capability audit).
7. Demonstrate one person conversation spanning existing QubeTalk + external transport.
8. Demonstrate one group-context interaction contributing to the same relationship without becoming a private message.
9. Demonstrate agent draft/bounded handling with disclosure boundary and receipt.

Acceptance scenario:

> The operator's relationship with John shows a QubeTalk/native exchange, an external direct message and a group interaction in chronological continuity. Each event retains its transport and audience. The agent can summarize the relationship, but when replying in the group it cannot disclose private direct-message content outside the permitted audience.

## Slice B — publishing + engagement

After Slice A:

1. PublicationQube.
2. Qriptopian Share → Publish integration.
3. One publishing adapter.
4. Engagement ingestion.
5. Participant resolution from engagement.
6. Convert engagement into ConversationQube.
7. Demonstrate publication → comment → agent/user reply → relationship continuity.

- webhooks vs polling;
- history/backfill limits;
- direct-message access restrictions;
- group access restrictions;
- publication APIs;
- comment/reply APIs;
- rate limits;
- media limits;
- whether user-token or business/page-token access is required;
- ToS/automation constraints.

Do not design user-facing promises beyond what the official access surface actually permits.

# 27. Ratification decisions proposed by v0.2

This specification proposes the following decisions for ratification:

1. QubeTalk is formally a **communications membrane**, not chat/inbox software.
2. RelationshipQube is the longitudinal continuity object above channels/platforms.
3. GroupQube is a first-class, temporally-aware social context.
4. ConversationQube is episodic/topic-oriented and can span platforms.
5. MessageQube is immutable/source-preserving and can appear in multiple contextual views without duplication.
6. PublicationQube and EngagementQube are separate from messaging but share the same participant, authority, receipt and routing substrate.
7. The rule **Context can inform; audience constrains disclosure** is constitutional for QubeTalk.
8. The rule **External communication is input, never authority** is constitutional for QubeTalk.
9. Platform adapters are capability/transport layers only; constitutional policy remains above them.
10. The next build is the conversation-continuity vertical slice, followed by publishing/engagement.

# 28. North-star user experience

The system is successful when the operator can say:

> "Tell John on WhatsApp that Friday works."

and QubeTalk can resolve the correct John, the correct ongoing conversation, the permitted context, the requested transport and the acting persona; send under the operator's or delegated agent's authority; record the receipt; ingest John's later Telegram reply into the same longitudinal relationship; recognize John's contribution in a shared group without confusing it with a private exchange; and preserve continuity when John later comments on a publication.

The platforms remain visible as provenance and available transports, but **the conversation belongs to the people, not the platforms.**
