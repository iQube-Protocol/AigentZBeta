# Amplify build-output cap resolved — the artifact was counting `.next/trace` (2026-08-02)

**Status:** resolved. First successful deploy: commit `e96076c`, 2026-08-02 ~23:30 UTC, after
eight consecutive size failures.

## The one-line cause

Amplify's measured "build output" includes `.next/trace` — Next's build diagnostics log,
~12.4 MB and slightly different every build — and `.next/types` (~10.2 MB of generated route
type declarations). Neither is read by anything the artifact serves. Removing both
**post-build, before packaging** cleared the cap with headroom.

## How it was found, and why it took eight builds

Every earlier cut was verified as *safe* but never verified as *counted*:

| Cut | Bytes removed where aimed | Effect on the reported artifact |
|---|---|---|
| README/CHANGELOG/HISTORY prune | ~0 (never traced into standalone) | — |
| `.d.ts` / `.map` prune | ~0 (never traced) | — |
| 3 unused vendored pdf.js builds | −6,249,974 from `.next/standalone` | **−1,954** |
| `.next/cache` (pre-build removal) | regenerated by the build | **−1,506** |
| Book evidence-matrix trace exclusion | −125 KB from the trace set | (within noise) |

The decisive arithmetic: the **unaccounted residual** (`reported − standalone − static`) held at
~12.2 MB across builds — and when the whole-tree ledger finally enumerated every child of
`.next`, that residual matched `.next/trace` to within 171 KB (trace varies per build):

```
unaccounted residual, 22:12 build : 12,247,115
unaccounted residual, 22:55 build : 12,245,617
.next/trace, measured 23:12       : 12,416,650
```

## What the measured artifact IS and IS NOT

- It is **not** `du -sb .next`: the tree measured 344,514,141 while Amplify reported 230,881,620.
- It is **insensitive to `.next/standalone` content**: −6.25 MB there moved the report by −2 KB.
- It **does** count `.next/trace` (demonstrated by the residual match and by the passing build
  after removal).
- Run-to-run variance at identical source exceeded 180 KB (npm install is non-deterministic and
  trace size varies) — which is why sitting <1 MB under the cap was a coin flip and one no-diff
  build passed mid-failure-streak.

## The enforcement (all in `amplify.yml`, end of the build phase)

1. Whole-`.next` ledger: every child enumerated by `du -sb .next/* | sort -rn`, before and after
   removals, plus the signed delta against the 230,686,720-byte cap. Printed **last** so it lands
   in the readable tail of the log.
2. Post-build removals: `.next/cache`, `.next/trace`, `.next/types`.
   `required-server-files.json` untouched — Amplify reads it.
3. Integrity checks run **after** the removals: cache absent, `BUILD_ID` present, `server/` and
   `static/` present. A removal that takes something real fails the build, not production.

## Rules this incident ratifies

- **Never prune what you have not measured as counted.** Safe ≠ effective; three safe prunes
  reclaimed zero measured bytes.
- **Measurements print at the END of the build phase.** Numbers above the compute-composition
  block sat unread for three builds.
- **≥5 MB headroom is the floor** (Al's requirement) given the demonstrated run-to-run variance.
- YAML plain scalars must not contain `": "` — two commands silently became YAML maps this way.
